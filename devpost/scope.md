# ClauseMap — Submission Preflight Inspector

ClauseMap helps an individual Build With AI: Basics entrant inspect a public GitHub repository before submitting, find verifiable gaps, and see which submission requirements still need human confirmation.

## The Unique Kernel

Each automated finding joins **an actual observation of the entrant's repository** with **the official rule that makes it relevant**. The report distinguishes observed success, observed absence, failed verification, and the entrant's own confirmation. It never implies that the overall submission or eligibility has been certified.

## Who It's For

An independent developer, student, or creator finishing a hackathon project with only hours left before submission. They want to avoid losing an opportunity to a preventable repository or document mistake; today they must compare the repository and submission materials against lengthy rules by hand.

## The Core Loop

The entrant enters a public GitHub URL and runs Preflight. ClauseMap checks live public repository data, shows the status and evidence for repository access and the three required planning documents, and lists requirements that need human confirmation. The entrant opens a failed finding to see what was observed, the matching official rule, and the next action; after fixing the repository, they rerun the same check and see a new result.

## Inspiration & Identity

A refined, minimal preflight inspection dashboard: precise information hierarchy and a calm, instrument-like feel rather than a chatbot. [Linear](https://linear.app/) and editorial dashboards are visual references, with a distinct ClauseMap identity to be defined in the PRD.

## Why This Matters to the Learner

The learner wants a polished, genuinely functional entry with a compelling one-minute demonstration. Reliability and visible evidence should carry the design. The project also practices taking an AI-assisted product from a clear scope through verification and delivery.

## What "Working" Looks Like

In a one-minute screen demonstration, a real public repository is checked; a missing planning document appears with the corresponding official rule; the document is added; a fresh check changes that finding to **Verified**. A separate inaccessible or constrained case yields **Unable to verify**, never a false success or a false missing-file claim. The demo video and public repository remain submission deliverables; deployment is optional.

## The POC Boundary — Must Have

- One competition only: **Build With AI: Basics**, using the current [Official Rules](https://learn-ai-basics.devpost.com/rules) as the authoritative source. Rule wording and links are curated and checked, not generated from arbitrary pasted text.
- Accept a public GitHub repository URL and inspect live public data. Confirm public accessibility only when it can actually be observed.
- Check for files named `scope.md`, `prd.md`, and `spec.md` across the repository. The root and Skill Pack's `devpost/` path may be checked first, but neither is an exclusive valid location: **Project Requirements → What to Create** in the [Official Rules](https://learn-ai-basics.devpost.com/rules) names the documents without prescribing a path. Each document gets its own finding and rule reference. File presence alone does not prove its contents or that it was generated by the Skill Pack.
- Use these distinct states: **Verified** = real, inspectable machine evidence for the specific claim shown (such as a public repository or a named file's presence); **Missing** = a required file is absent after a sufficiently complete, reliable repository-wide check; **Unable to verify** = access or inspection failed or evidence is insufficient; **Needs confirmation** = a human-only item is unanswered; **Self-confirmed** = the entrant says it is done, without machine verification. Self-confirmed never becomes Verified.
- Show human confirmation items for the demo video, entrant eligibility, and Devpost submission form, with links to their relevant sections of the [Official Rules](https://learn-ai-basics.devpost.com/rules). These are not silently included in an automated pass claim.
- Each finding exposes the observation or verification limit, the applicable official rule, and the entrant's next action. No overall compliance score, certification, or eligibility verdict.

## Failure Principles

- An invalid GitHub URL, nonexistent or private repository, network/API outage, rate limit, or an ambiguous GitHub response produces **Unable to verify** for affected automated checks, with a specific reason when known. GitHub's public response may not distinguish a nonexistent repository from a private one; the report must not claim which it is without evidence.
- **Missing** is reserved for a successfully inspected public repository only when the check has enough reliable repository-wide coverage to establish that a named document is absent. If the file tree or equivalent search is incomplete, truncated, or limited in scope, the result is **Unable to verify**. A failed file request or absence from preferred paths alone is insufficient.
- The feasibility and technical method for obtaining sufficiently complete repository coverage are decisions for `4-spec`; this scope defines the evidence threshold, not a GitHub API implementation.
- A recommendation is not a mandatory check. For example, the official rules say a public repository **should** include an open source license; this first version does not flag its absence as a violation.
- Rule evidence is mapped to each check, not merely linked as one generic rules page. If the official rules change, the mapping needs review before making current compliance claims.

## Acceptance Criteria

1. A reachable public GitHub repository containing the three named documents, including outside the preferred paths, produces live, evidence-backed **Verified** findings for public access and each observed file's presence, without claiming its content or origin was verified.
2. After a sufficiently complete, reliable repository-wide check, absent named documents are identified as **Missing**, each with the correct official rule and a concrete repair action. Adding a document and rerunning changes only the result supported by the new observation.
3. Invalid, inaccessible, nonexistent, private, rate-limited, or otherwise uninspectable cases never produce **Verified** or **Missing** for checks that could not be completed; they explain **Unable to verify**. Incomplete or restricted repository coverage also cannot yield **Missing** for a file not found.
4. Human-only requirements begin as **Needs confirmation** and can become **Self-confirmed** through an explicit user action, without becoming machine-verified or contributing to an overall certification claim.
5. The demo uses real checks and shows a failure → fix → recheck sequence, with no scripted verdicts presented as inspection results.

## Later

Additional competition templates; GitLab and Bitbucket inspection; reliable extraction of rules from pasted text; richer checks of submitted video and project materials, only when they can be verified accurately.

## Explicitly Cut — Out of Scope

- Arbitrary-rule parsing, full RAG, and paid AI APIs: unnecessary for this competition-specific, evidence-first proof of concept.
- Login, database, and submission automation: they add infrastructure or authority without proving the core loop.
- Additional automated checks, including license, video length, and personal eligibility: these either fall outside the chosen demo, are recommendations, or cannot be reliably established from a GitHub URL alone.
- A total readiness score or claim that the entrant is eligible or compliant: the report cannot verify the full submission.
